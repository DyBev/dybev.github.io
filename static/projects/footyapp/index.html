Footyapp

A fantasy football app built for a fantasy league that my friend was running, they wanted to detach themselves from the FPL format and have a bit more interaction between the league members

Built on a core concept of a "Auction" where the entire league gets together and then place bids on each player where the league manager leading the auction

Each player get's a total of of "300 million" to spend on bidding for players and a total of 15 players per team

The league bidding happens 2/3 times per season depending on how the league was run sometimes the league members spent all of their cash in the first 2 auctions so the 3rd is skipped

If members wanted to buy new players they would need to forefit a previous player to buy the new one, but of course there is no gurantee, since other players also have the opportunity to bid, as you can imagine there were a few late season upsets

Sadly this is one of those projects that outgrew me, legacy decisions combined with me still learning and growing as an engineer, some decisions I made made it difficult to continue itterating and improving the core app

I also ended getting bitten by the changes in the API provider, they made a change that meant that seasons past the 2024/2025 season were not available on the free plan

Details

Read about the details and choices I've made

Database

Google - Firebase:Firestore

  • Serverless Document based database it was a really nice choice with it's extensive API and it's batteries included approach meant it was really easy to integrate features like realtime updates
  • Easy intergation with the FE code made it very easy to intergate new pages and features to the app

Backend

POC - Python

  • Built out my initial POC for the backend in a locally run python script
  • Pythons ease of use was an easy choice for a prototyping language
  • Strong integration with SQL lite making it easy to manage and maintain scores

Data Source

api-football.com

  • At the time there a was a generous 100 per day calls on the free tier and it included the latest Premier league season
  • Easy to use API with code samples for Python and Go available
  • Had endpoints for the full league timetable individual matches individual teams and players making it easy to build out the necessary data for the app

Backend

final implementation - Golang

  • After a year of running the updates manually I made the decision to re-write the BE to run autonomously using AWS-step functions(lambdas) I chose Golang for it type security and it's speed and ease of deployment to the AWS lambda ecosystem
  • Strong typing made it easy to avoid any type errors, which would happen occasionally in the python codebase
  • Go langs approach to errors as an active thought made it effortless to gracefully handle any errors with errors getting logged in cloudwatch it was easy to remediate any lingering issues

What would you do if?

Essentially an self-appointed FAQ

You would build it all again

I really learned a lot from this project

I think the biggest mistake I made when I built this was the lack of planning on my side

The premise and the idea of the app was really simple but it's just a special UI to replace a google spreadsheet, it didn't feel like there was any features to the app itself, just a wrapper UI

I think ideally I would flesh out some of the features for the app a bit more, like it would be nice for there to have been a "pre-auction" where people could pre-register interest for players and who they would be willing to drop for it, that would get revealed to everyone on the league manages appointed league auction day

Or perhaps some features relating to the individual players themselves, for example seeing their performance on a match by match basis rather than a week by week basis

What do you think you learned the most

Making use of managed services is a good idea

Going into the project I was really excited about renting my own bare-metal server and deploying my own API + database there, hence why the initial POC was written with a locally run Python

I really should have gone and done the leg work of research before I started my development, because once I realised the requirements and the challenges that come with self-hosting I had already done a lot of the difficult work of coding out the cron the update scripts etc

The firebase decision felt like an "oh crap - I'm not ready for this" moment, but really I would not have learned that without the ambition

Ultimately making judgement errors is human, and I much prefer the judgment errors happen in my own time rather than they happen in production infront of 10s of thousands of users who are relying on what you build to work
